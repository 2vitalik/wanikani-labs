# T35 · Варіанти: межа сесії, буферизація, діфи стану, модель нотифікацій, налаштування, рендер

## 1. Як зрозуміти, що «позаймався»

- a) **пауза ≥ gap між моментами подій** (T31) — просто, точно завдяки міткам WK, ретро з 2024; мінус — затримка gap + полл. **Рекомендую**, дефолт 15 хв.
- b) фіксований розклад (щогодини / щодня) — нуль евристики, але «звіт о 14:00, а закінчив о 13:05» і порожні звіти; лишаємо як окремі види (`hourly`, `daily`), не як заміну.
- c) гібрид a + кнопка `⏹ End now` на живому повідомленні — знімає затримку, коли ти поруч із телефоном. **Рекомендую разом з a.**
- d) «`due` перестало падати» / `summary` — те саме, що a, але грубіше (summary оновлюється щогодини); ні.
- e) адаптивний gap (медіана пауз останніх сесій × k) — цікаво, але непередбачувано для користувача; ні.
- f) reopen після ручного закриття, якщо події прийшли в межах gap — зручно, але фінал уже надіслано → редагувати ще раз; робити лише якщо «нова сесія» дратуватиме (T36 Q12).
- Поріг 10 / 15 / 20: таблиця T31 §3 — 10 хв рве ~10% сесій, 20 майже нічого не додає до 15.

## 2. Де тримати «незакінчене» (події, які ще не пішли у звіт)

- a) прапорці на подіях (`delivered` для сесійних маршрутів) — розмазує стан по 100k документів, важко перебудовувати; ні.
- b) **сесія як документ + `reports` за ключем** — стан у двох маленьких колекціях, ідемпотентність за ключем, rebuild безболісний. **Рекомендую.**
- c) буфер у памʼяті бота — губиться на рестарті; ні.

## 3. «Що змінилось» — як отримати стан «до»

- a) снапшоти матриці (щодня / на початку сесії) — просто, але не ретро, гранулярність — лише там, де знімали, і треба чистити.
- b) реплей `history` до моменту T — точно; 39k версій `assignments` на акаунт → секунди; дорого на кожне повідомлення, ок для рідких запитів.
- c) **`reverse_apply` подій вікна над поточною матрицею** — точно для будь-якого вікна (переходи несуть `from → to`), миттєво, без нових даних. **Рекомендую**; b — як тест-оракул і для `since <дата>` далеко в минулому.
- d) список змін по айтемах напряму з подій — доповнення до c (цитата «що саме»).

## 4. Модель нотифікацій

- a) маршрути як є + настройка `mode: instant | session | daily` — мінімум змін, але «reviews у режимі daily» = різні речі під одним іменем, а унікальність `(account, category, chat)` не пускає дві нотифікації в один чат.
- b) **нотифікація = вид × ціль** (`kind` замість `category`, унікальність геть) — розширення T30, не переписування; пресети/права/picker працюють. **Рекомендую.**
- c) рушій правил (`if kind in … and level ≥ … then …`) — максимум влади, UI-пекло; колись як L4 через export/import, не через кнопки.
- d) спільна нотифікація для кількох акаунтів (обидва в одне повідомлення) — окремий вид `combined`, потім (T36 Q14).

## 5. Налаштування: як показувати

- a) усе на одній картці — 15+ кнопок, ні.
- b) **шари L1 / L2 / L3 з реєстру** — «клац-клац» і кроляча нора одночасно. **Рекомендую.**
- c) майстер при створенні (5 кроків) — ні: дефолти + картка швидші; єдиний «майстер» — `➕ Add` = вид → ціль (два кроки).
- d) конфіг-файл/JSON у чаті — L4 як export/import, коли блоки стабілізуються.
- e) текстові темплейти — L4 після d; до того блоки + опції покривають 90%.
- `int`-настройки: цикл пресетів на кнопці (рекомендую) vs `[−] 15 [+]` (два тапи на крок, більше кнопок) vs діалог (для L3).

## 6. Рендер карти рівнів

- a) **emoji-смуга** (🔒🩷💜💙🩵🔥, 10 клітинок на рівень) — наочно, однакова ширина в усіх клієнтах, кольори = стадії. **Рекомендую** як дефолт.
- b) числа в `<code>` — точно, компактно; як `style: counts`.
- c) блоки `▁▂▃▅▇` / `█▓▒░` — монохром, стадії не видно; ні.
- d) PNG (Pillow, палітра wkstats) — найкраще візуально, потрібні шрифт, рендер, кеш; фаза «потім», той самий `level_rows`.
- e) web-сторінка з посиланням — фаза web (T01).
- Діф: `inline` (`5→3` справа) — компактно (рекомендую для сесії); `before_after` (дві смуги) — наочніше, вдвічі довше (для `around` з малим N); цитата зі списком айтемів — завжди доступна як блок.

## 7. Живе повідомлення

- a) **одне повідомлення, редагується кожен полл, фінал — edit** — нуль спаму, прогрес видно одразу. **Рекомендую.**
- b) лише фінальне — простіше, але 15–20 хв без зворотного звʼязку.
- c) нове повідомлення кожен полл — спам; ні (це і є нинішній `live`, для кого треба — він лишається окремим видом).
- Звук у кінці: `finalize: new` — коротка відповідь на живе, опція L2.

## 8. Планувальник для планових видів

- a) job на кожну нотифікацію в APScheduler — стан у памʼяті, ресинк на рестарті та при кожній зміні; ні.
- b) **`tick` щохвилини + `next_run_at` у документі** — стан у Mongo, рестарт-безпечно, multi-user. **Рекомендую.**

## 9. Дефолти нового акаунта

- a) `live + milestones` (як зараз) — шумно: повідомлення кожні 5 хв під час сесії.
- b) **`session + milestones`** — тихо й змістовно; `daily` — один тап. **Рекомендую.**
- c) `session + daily + milestones` — три одразу; для тебе, мабуть, так, для новачка — b.

## 10. Мінімальна сесія

- a) `min_items` = 3: менше — без окремого повідомлення (живе, якщо було, лишається) (рекомендую).
- b) без мінімуму — 2vitalik отримував би сотні «1 review».
- c) менше N → доклеїти до наступної сесії — ламає визначення сесії; ні.

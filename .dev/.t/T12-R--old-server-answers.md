## Як я зрозумів

- **Q1:** cron `wanikani_fetch.py` крутиться на **vv1** і **живий** → на сервері є хвіст після 2026-03-28, діра до запуску нового бота закриється майже повністю (лишиться лише інтервал між останнім rsync і першим sync на vv3 — і той стиснеться в одну подію на обʼєкт).
- **Q2:** команди на сервері й rsync виконуєш **ти**; я — порівняння дерев, імпорт, перевірки.
- **Q3:** дані з сервера — в **окрему теку `~/Giga/data/wanikani-server`**; злиття з `~/Giga/data/wanikani` — після мого порівняння. Імпортувати можна прямо з нової теки (ідемпотентно), зливати теки не обовʼязково.
- **Q4:** старий cron **лишається ще 1–2 тижні** після запуску бота на vv3, потім вимикаєш. Наслідок: перед вимкненням — ще один rsync + доімпорт (той самий сценарій, хвилина роботи).

## Твої кроки (копіпаст)

На vv1:
```sh
crontab -l | grep -iE 'wanikani|mochi'
# з рядка cron: розклад і шлях до mochi → далі D = <mochi>/data/wanikani
D=<mochi>/data/wanikani
du -sh $D; find $D -name '*.json' -newermt 2026-03-29 | wc -l
find $D -name '*__2026-*.json' | sed -E 's#.*__([0-9-]+)__.*#\1#' | sort | tail -1
```
Очікую: розклад cron, розмір ~2 GB, десятки тисяч файлів після 03-29, остання дата ≈ сьогодні.

З Mac (`<D>` — той самий шлях; `-a` зберігає mtime, `--delete` не вживати):
```sh
mkdir -p ~/Giga/data/wanikani-server
rsync -avn --stats vv1:<D>/ ~/Giga/data/wanikani-server/ | tail -12    # dry-run: скільки файлів
rsync -a --info=progress2 vv1:<D>/ ~/Giga/data/wanikani-server/         # ~2 GB, 300k+ дрібних файлів — кілька хвилин
```
Кинь у чат вивід `crontab -l | grep …` і хвіст `--stats` — далі мої кроки.

## Мої кроки після цього

- порівняти дерева: сервер має бути надмножиною Giga (ті самі імена, ті самі байти); різниці — у C-тікет;
- `uv run wklabs import-files ~/Giga/data/wanikani-server` → `uv run wklabs rebuild-events -y` → звірка лічильників (файли ↔ `history`) до одиниці;
- далі за T10: дамп `history` на vv3 після деплою бота; через 1–2 тижні — повторний rsync + доімпорт, тоді вимикаєш cron.

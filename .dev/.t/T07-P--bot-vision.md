# T07 · Бачення бота: продукт, фічі, режими (фон дорожньої карти)

`2026-09-10` · 💡 proposal

Контекст:
- твоя розповідь з чату 2026-09-10: загальний задум бота — що хочеться колись мати; це **не ТЗ і не план**, а фон, щоб було зрозуміло, куди рухаємось; реалізація — поступово, маленькими кроками, спершу лише те, що потрібно тобі (пілот);
- база — v1 з [T01](T01-P--architecture-v1.md): поллер + дайджести у форум-топіки; ключове обмеження звідти: історія ревʼю існує лише як діфи між поллами (`/reviews` порожній);
- позначки нижче: без позначки — твій задум (переказано і згруповано); ➕ — моє доповнення/пропозиція; ⚠️ — обмеження чи ризик, який треба врахувати.

## 0. Принципи (рамка)

- Пілот — для тебе; закладаємо multi-user / multi-account від початку, публічний реліз для комʼюніті — потім, коли бот стане адекватним.
- Усе налаштовується через бота: додати, прибрати, режим; дефолти розумні, щоб і без налаштувань працювало.
- Telegram зараз, Discord — колись. ➕ Тому шар доставки відокремлений від логіки: чистий рендер → модель повідомлення → адаптер (TG зараз, Discord потім). `digest.py` уже чистий — це і є початок.
- ➕ Похідне (сесії, стріки, статистика) перераховується з `history` / `events` (правило проєкту) → правила можна міняти заднім числом, а імпорт Giga дасть ретроспективу з 2022.
- Безпека токенів: read-only за замовчуванням, write — окремо й свідомо.

## 1. Трекінг прогресу (пріоритет №1)

### Сесії

- Що: після заняття — статус «що пройдено»: скільки ревʼю/уроків, ✅/❌, деталі в цитатах (які саме айтеми, успіхи, дрібна статистика).
- ➕ Сесія = кластер подій `reviewed` / `started` з паузою між ними < N хв (кандидати 10–15); закривається після N хв тиші. Одне «живе» повідомлення на сесію: редагується, поки сесія триває, фіналізується після закриття — без спаму.
- ⚠️ Гранулярність часу = інтервал поллу (5 хв): точні часи є лише для сесій через бота; для WK-сайту — «між поллами». ➕ Адаптивний полл: під час активної сесії опитувати `assignments` частіше (1 хв), у тиші — рідше.
- Режими (налаштування): миттєво (дайджест на полл — як зараз) · по сесії · погодинно · щоденно · будь-яка комбінація.

### Денний підсумок

- Раз на день (час — налаштування; ➕ дефолт ~04:00 локально, щоб «день» включав нічні заняття): ревʼю/уроки, точність, SRS-переходи, guru/burn, час у сесіях, рівень.
- Огляд по днях: сьогодні / вчора / тиждень / місяць. ➕ Формат — таблиця в моноширинному тексті або спарклайн з блоків `▁▂▃▅▇`; складніше — PNG-картинка (це вже сфера `web/`, бот лише показує).

### Стріки

- Ланцюжок днів; має бути мʼяким, щоб не демотивував.
- ➕ Механіки (усе — налаштування): поріг «день зараховано» (будь-яка активність або ≥ N ревʼю); заморозки (X на місяць, накопичуються); планові вихідні (напр. неділя не рахується); показ «14 днів · 1 пропуск» замість обнулення; ретроактивний підрахунок з `events`.

## 2. Сповіщення про зміни контенту WaniKani

- Нові предмети/уроки, правки (мнемоніки, значення, читання), приховані.
- Фільтр: лише мої (розблоковані/розпочаті) · усі · вимкнено.
- ➕ Для «моїх» — діф поля (що саме змінилось), для решти — коротко; окремо підсвічувати нові предмети на **поточному** рівні (впливає на «рівень 100%»).
- Є вже: топік `subjects`, події `subject_new / subject_updated / subject_hidden` — лишаються фільтри й деталізація.

## 3. Нагадування

➕ Ти не називав явно, але це частина «сповіщати про щось»:

- доступних ревʼю ≥ N; уроки доступні; прогноз ревʼю на добу (з `/summary`);
- тихі години; не нагадувати, якщо був активний останні X хв; «нагадай о …».

## 4. Режими доставки, акаунти, користувачі

- Три режими: приватний чат · група · форум (топіки за категоріями; бот сам створює — є).
- Кілька акаунтів (у тебе два); у кожного — свої налаштування, свої чати/топіки; можна трекати чужий акаунт read-only токеном.
- ➕ Модель: користувач TG → акаунти WK → **призначення** (чат або топік) на категорію повідомлень (`reviews · milestones · subjects · reminders · system`) → налаштування трьома шарами: дефолти в коді → акаунт → призначення. Це узагальнення нинішнього `routing.py` (kind → topic).
- ➕ Акаунти — в Mongo, додавання діалогом у приваті: `/add_account` → токен → перевірка `/user` → бот видаляє повідомлення з токеном. `.env` лишається для bootstrap твоїх акаунтів.
- ➕ Токени в Mongo шифрувати (ключ у env); `/remove_account` — з опцією видалити й дані.

### Токени: read-only vs write

- Read-only достатньо для всього, крім ревʼю та уроків через бота.
- ➕ У WK токен один, права — чекбокси при його створенні (`assignments:start`, `reviews:create`, `study_materials:create/update`, `user:update`). Бот за замовчуванням просить read-only; «грати через бота» вмикається лише коли доданий токен із write-правами (з інструкцією, які саме галочки); на 403 — пояснює, чого бракує.
- ⚠️ Перевірити при реалізації: чи живі `POST /reviews` і `PUT /assignments/:id/start` — GET `/reviews` WK уже прибрав (T01).

## 5. Ревʼю через бота

- Порядок черги — критично: рівні від старших · від молодших · поточний рівень спершу · за SRS-стадією · за типом (радикал → кандзі → слово) · випадково; розмір батчу.
- Ввід: вільний текст · вибір з варіантів · Anki-режим («памʼятаю / не памʼятаю»; ➕ відповідь під `<tg-spoiler>`).
- Керування відповіддю: «насправді правильно» / «насправді неправильно» (undo), пропустити, показати мнемоніку/інфо.
- ➕ Механіка WK: айтем зараховано, коли відповідено і значення, і читання (крім радикалів і кана-словника); кількість помилок визначає падіння SRS; результат — `POST /reviews` з `incorrect_meaning_answers` / `incorrect_reading_answers`. Перевірка значення — з толерантністю до одруків як у WK, читання — точно; romaji → кана автоконвертація для набору з телефона.
- ➕ Стан батчу — в Mongo, не в памʼяті: рестарт бота не губить сесію; відповіді у WK — одразу або пакетом наприкінці (налаштування).
- ➕ Уроки через бота: `PUT /assignments/:id/start`; контент (мнемоніки, приклади, аудіо) уже є в `subjects` — потрібна конвертація WK-розмітки (`<radical>`, `<kanji>`, `<vocabulary>`, `<reading>`, `<ja>`) у TG HTML; радикали без Unicode — лише картинкою (`character_images`).

## 6. Стратегії та статистика (à la wkstats)

- Стратегії проходження (старші рівні / молодші / поточний) — для кожної свій прогрес: скільки пройдено, що лишилось.
- Огляд рівнів: на рівень — айтеми за SRS-стадіями, скільки due, точність; сортування asc / desc / від поточного; вибірка за типом.
- Час на рівень (з `level_progressions`) і темп: «хочеш ≈ X днів на рівень → потрібно ≈ Y уроків і ревʼю на день», прогноз дати рівня 60; ціль задається в днях на рівень або датою.
- ➕ Точність з `review_statistics`: загальна, за типом, найпроблемніші айтеми (leeches).
- ➕ Ретроспектива з історії Giga (з 2022) — після імпорту (фаза 3 у T01).
- ➕ Усе це — функції в `lib` (чисті, над Mongo), щоб бот і майбутній `web/` рахували однаково.

## 7. Оформлення

- Telegram HTML (уже): жирний / курсив / моно / цитати / `<blockquote expandable>` / спойлери, посилання на WK; емодзі за SRS (є).
- ⚠️ Кольору й розміру шрифту в TG-тексті нема. ➕ Великі кандзі/слова — картинкою (Pillow + японський шрифт; це ж вирішує радикали без Unicode) або окремим рядком `<b>` + `<code>`.
- Інлайн-клавіатури для відповідей і меню налаштувань. ➕ Кастомні емодзі доступні лише преміум-ботам — не розраховувати.

## 8. Для комʼюніті (згодом)

- Multi-tenant від початку (п. 4); ліміт WK 60 req/хв — на токен, тож масштабується сам.
- ➕ i18n (EN дефолт, UA), приватність (шифрування, видалення на вимогу), ліміти на користувача, онбординг у `/start`, публічний README.
- Discord — адаптер доставки поверх тієї ж моделі повідомлень; логіка не міняється.

## Що вже є у v1 (на що спирається бачення)

- Поллер + `events` (усі види з T01) → топіки форуму за `routing.py`; рендер `digest.py` чистий — база для «моделі повідомлення».
- Акаунти й адміни — з `.env`; команди лише для `TG_ADMIN_IDS`; `/status` дає рівні, SRS, ревʼю due.

## Пропозиція черговості (маленькі кроки; кожен старт — окремий тікет або задача)

1. Запуск із реальним Telegram + деплой (уже в STATUS).
2. Сесії + денний підсумок + стрік (п. 1) — з дефолтами, без UI налаштувань.
3. Каркас налаштувань (`settings` у Mongo, три шари, меню `/settings`) — щойно зʼявиться друга настройка.
4. Фільтри `subjects` (п. 2) і нагадування (п. 3).
5. Статистика рівнів / темпу / стратегій (п. 6) — read-only, багато цінності за малу ціну.
6. Акаунти й призначення в Mongo, приват і група (п. 4) — підготовка до multi-user.
7. Ревʼю через бота (п. 5): спершу Anki-режим (найпростіший UX), потім текстовий ввід, потім уроки.
8. Публічний реліз, i18n; Discord.

Чому write-фічі наприкінці: потребують перевірки WK write API і найскладнішого UX; усе до них цінне вже з read-only токенами.

## Відкрите (вирішувати при реалізації відповідного кроку, не зараз)

- Межа сесії: N хв тиші (кандидати 10 / 15) і чи вмикати адаптивний полл.
- Межа доби для підсумку і стріка (кандидат 04:00) та мінімум активності для «дня».
- Сховище налаштувань: одна колекція `settings` з шарами vs документ на акаунт.
- Read-only і write токени одного акаунта: один запис із правами vs два токени.

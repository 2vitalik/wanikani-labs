# T11 · Чистий лист чи доповнення локальної бази перед дампом на сервер

- схема — [T01](T01-P--architecture-v1.md), стан імпорту — [T08](T08-C--import-history.md), план — [T10](T10-P--full-data-plan.md).

## Коротко

Доповнювати, не дропати. «З нуля» дає по `history` **той самий результат**, але втрачає baseline 23.08, який з API вже не дістати. Надійність дає не дроп, а звірка лічильників (яку ми й робимо).

## Чому результат той самий

- `history` — append-only, unique на `(resource, account, resource_id, data_updated_at)`; будь-який імпорт того самого джерела вдруге дає 0 вставок (перевірено на Giga: 319k файлів → 0 нових при повторі, тест `test_importer.py`). Тобто множина версій не залежить від порядку і кількості прогонів.
- `events` — похідне, `rebuild-events` дропає й переграє все з `history` за 7 с; жодної логіки, яку не можна відтворити.
- `current`-колекції — стан «зараз», відновлюються `wklabs sync --full` за ~20 с.

## Чому «з нуля» — це втрата

- Baseline 2026-08-23 (23 840 версій) — знімок стану кожного обʼєкта на той день. API віддає лише поточний стан, тож після дропу цей знімок не повернути. Без нього діра 2026-03-28 → сьогодні стає **однією** стиснутою подією на обʼєкт замість двох (03-28 → 08-23 → зараз).

## Що дає надійність замість дропу

- Звірка до одиниці: файли ↔ `history` по категоріях і акаунтах (T08 — зійшлося), те саме для zip і для rsync-хвоста (T10 крок 4).
- Інваріанти, які перевіряються запитом: нема двох версій з однаковим `data_updated_at` і різним змістом (перевірено між акаунтами — 0); `events` після rebuild = детермінована функція `history`.
- Якщо все ж хочеться «контрольного» прогону — збірка в окрему БД `wanikani_labs_check` з тих самих джерел і порівняння множини версій (мінус baseline) з основною. Це той самий факт, що й звірка лічильників, лише дорожче; робити не раджу.

## На сервер — лише `history`

- `mongodump --collection history` → `mongorestore` на vv3 → перший sync там сам стає baseline → `rebuild-events -y`. `current`/`sync_state`/`events` не переносити: інакше бот на vv3 продовжить інкрементально з локального `updated_after` і вивалить у Telegram дайджест за всі тижні між локальним sync і деплоєм.
